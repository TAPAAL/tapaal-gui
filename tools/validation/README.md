# Faster validation for the TAPAAL GUI

Start by running one real editor workflow on every PR and by turning GUI bugs into small, behavior-based regression tests. Use change-impact reports to guide extra validation and to show reviewers where coverage is missing. Keep the current merge workflow during the pilot.

## Runnable prototypes

Run the existing suite and the editor smoke from the repository root with JDK 17, Xvfb and xauth.

```sh
xvfb-run -a -s '-screen 0 1280x900x24' ./gradlew --no-daemon build guiSmokeTest
```

- **Editor workflow.** Launch the real application with a one-place model, choose the Place tool, click the visible canvas, undo and redo through the menu actions, then save, close and reopen. The test compares place names and token counts on the canvas and in the model, and verifies that Save clears the dirty state. It uses action and menu names and the canvas bounds. Startup opens a known file and reopen uses the UI controller's file entry point, so native file choosers remain a separate test opportunity. Gradle captures application output and JUnit failures in `build/test-results/guiSmokeTest/`. Failed workflows capture the display and current model in `build/reports/gui-smoke/`. [Workflow test](../../src/test/java/net/tapaal/gui/GuiWorkflowSmokeTest.java)
- **Saved-document regression.** Open `before.tapn`, drag place P0 with the real mouse from its on-screen bounds, choose File > Save and compare the file with `expected.tapn`. The two fixtures differ only in the place position and the attached arc end point. The comparison ignores indentation, attribute order, comments, CDATA and escaping. It compares element order, attribute values and text exactly. A failure names each differing path, for example `/pnml/net[@id='MovePlace']/place[@id='P0']/@positionY`. It also writes the saved file, the expected file, the differences and a screenshot to `build/reports/gui-smoke/place-drag-save/`. `guiSmokeTest` starts a fresh JVM for each explicitly included smoke-test class because the application window is static. [Regression test](../../src/test/java/net/tapaal/gui/PlaceDragSaveRegressionTest.java), [Fixtures](../../src/test/resources/validation/move-place)
- **Caught-exception observation.** `CaughtExceptions.report(site, throwable)` does nothing in production. Tests use `CaughtExceptionRecorder` to record each report for one test. A recorded failure fails the test unless the test allows it or takes it and asserts on it. The trial instruments the writer's save catches, the startup file-open catch and the optional native desktop hooks. The regression test allows the three native hooks on Linux. It then selects a JAXP transformer factory that throws and saves a second move. The writer reports and swallows the failure. The file keeps its previous content and the editor reports no unsaved changes. [Hook](../../src/main/java/dk/aau/cs/debug/CaughtExceptions.java), [Recorder](../../src/test/java/net/tapaal/gui/CaughtExceptionRecorder.java)
- **Legacy document regression.** The existing transport-arc loader case now checks the visual and semantic weights and the endpoint marking before and after serialization. It exercises the original regression through the same loader and writer the application uses. Run it on its own with `xvfb-run -a ./gradlew test --tests '*TapnXmlLoaderTest*TransportArc*'`. [Loader test](../../src/test/java/dk/aau/cs/io/TapnXmlLoaderTest.kt)
- **Advisory impact report.** Run the command below on an actual historical change. The report includes changed paths, mapped capabilities, possible failure severity, invariants, historical examples, suggested checks, and missing evidence. A shared dependency or an unmapped path selects broader validation. The prototype leaves execution evidence empty because it only analyzes the supplied commits. [Impact map](capabilities.json), [Report script](assess_change.py)

```sh
python3 tools/validation/assess_change.py '7fc9bfd1a^1' 7fc9bfd1a
```

PR 388 selects broader validation and highlights serialization, verification integration, and simulation. PR 393 selects the baseline plus editor checks. A workflow-only change at `2b1639c13` exercises the unmapped-path fallback. Treat these as examples of how the rules work. The rules were informed by the audited bugs.

The legacy regression failed with the pre-fix `TransportArc` class because the loaded model returned weight 1 for a serialized weight of 2. For the workflow failure check, changing the fixture's initial token count produced the expected assertion failure and captured the display, model and test output.

## Test architecture and developer workflow

1. **Keep JUnit and use the shallowest useful entry point.** Use direct tests for query validation, markings, transformations and serialization invariants. Run a small Swing smoke suite for workflows whose wiring matters. The existing test worker and Xvfb can run both today. Start headless extraction where the audit found a concrete problem. Trace the loader-to-frame initialization and move editor-only setup to the application boundary so model and compatibility checks can run independently.
2. **Use names for Swing controls and state for assertions.** The prototype uses JDK `Robot` for input on the custom canvas and JUnit for state assertions. As scenarios grow, assign stable `setName` identifiers to controls that tests use and resolve them on the Swing event thread. Evaluate AssertJ Swing on a dialog and a canvas flow before adding it. Its component finders and fixtures can shrink test code. The comparison should measure Java 17 compatibility, cold and warm runtime, and repeatability on Xvfb. Screenshot-based automation is useful for investigating layout and rendering, while component lookup gives more stable workflow tests. [AssertJ Swing project](https://github.com/assertj/assertj-swing), [AssertJ Swing overview](https://assertj-swing.readthedocs.io/en/latest/assertj-swing/)
3. **Keep the same command inside local and CI isolation.** The smoke passed in a disposable Linux namespace with a private home, no network and its own Xvfb display. For untrusted PR builds, run the command in a disposable Linux VM with a scratch checkout, restricted network, and no mounted host home, SSH agent, or credentials. On GitHub, use the hosted Ubuntu VM. For local developer or agent use, give each run a fresh VM from a pinned JDK 17/Xvfb image. Optional VNC/noVNC should expose that VM's display through authenticated, time-limited access. Export test XML, logs and screenshots from the VM before automatic teardown. The namespace run validates the test command and artifact path. Local VM provisioning and interactive access remain to be piloted. [GitHub hosted runners](https://docs.github.com/en/actions/how-tos/write-workflows/choose-where-workflows-run/choose-the-runner-for-a-job)
4. **Make one architectural seam testable at a time.** Start with explicit originating-tab context for a verification request and result. Keep existing entry points delegating to the current implementation, add a fixture for switching tabs during an outstanding request, then migrate one caller at a time. The local `implement/issue-1-current-tab-seam` branch already contains work in this direction. A second candidate is the loader returning model and presentation data before Swing creates components. Compare both implementations on existing fixtures during migration and remove the old path after the invariants pass. Use an integration branch only when intermediate changes cannot preserve existing behavior.

## GitHub proposal

Keep the existing build job as the baseline. Add `guiSmokeTest` under its existing Xvfb setup in the first CI PR. Publish a job summary and upload JUnit XML, process logs, and screenshots on failure. Run the impact analysis against the PR base and head, using the target branch's rules to decide what validation to request. Use `pull_request` on a GitHub-hosted VM with read-only permissions and no secrets for candidate execution. [GitHub workflow syntax](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax)

| Tier | Trigger | Validation |
| --- | --- | --- |
| Fast | Every PR | Gradle build and current tests, editor smoke and obvious targeted checks. Keep visibility on cold and warm runtime. Aim for a five-minute core suite after measuring CI. |
| Extended | Nightly, on demand for shared or unmapped changes, and for affected high-impact capabilities | Full editor paths, dialog interactions, import/export compatibility, two-tab undo and query cases, simulation and recorded-result replay. Unknown impact selects the broader suite once it exists. |
| Full | Release candidate | Run extended coverage against packaged builds. Exercise platform-specific file dialogs and app startup, supported file formats, representative performance scenarios, and independent review for changes that can alter the GUI's query or displayed result. |

The PR summary should include the exact base and head SHAs, diff summary, affected capabilities with path evidence, failure modes and severity, selected suites, executed suites and outcomes, timings and artifact links, and missing coverage. Mark skipped, cancelled and unimplemented checks explicitly. Associate evidence with the tested SHA and distinguish the PR head from a GitHub merge commit. Use verified test results for pass/fail. Keep the impact assessment advisory while the team measures which predictions are accurate and which suites are reliable.

## Prioritized roadmap

| Order | Work | Evidence of progress |
| --- | --- | --- |
| 1 | Add the smoke command and failure artifacts to current CI. Collect duration and repeat failures over representative PRs. | A contributor can reproduce the job locally and diagnose failures from its artifacts. |
| 2 | Extend editor coverage in small increments. Start with one arc or transition edit, a component copy preserving names, and a two-tab undo or query response. Add one compatibility fixture with each such bug fix. | The new check fails against the original bug and passes after the fix. |
| 3 | Move one loader or query-validation path out of global Swing state. Reuse the smallest existing boundary and migrate one caller with behavior tests. | A previously display-dependent check passes headless, with the same compatibility assertions. |
| 4 | Add the advisory summary. Give implemented suites stable IDs and link those IDs, regressions and invariants to the handful of shared components in the map. Use imports and callers for hints, and preserve broader validation for unknown paths. | Reviewers see why suites were selected and can distinguish suggested checks from executed checks. |
| 5 | Pilot a disposable VM for untrusted local runs, then add simulation, native-dialog and release checks using the same test entry points. Track latency, coverage gaps, flakes and regressions caught. | An agent can run the workflow in a fresh VM and export diagnostics after a failed run. |

The first useful architecture PR is one that deletes a dependency on the current frame or tab and supplies a regression test that would fail without the change. Record those results before expanding the capability map or adding branch-management rules.
